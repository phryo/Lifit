# Lifit — 健診の、その先へ。

健診結果の理解から、具体的な行動・記録・振り返りまでを3〜5分で体験できる、日本語のインタラクティブプロトタイプです。ローカル開発環境向けに実装しています。医療システムや診断AIではありません。

## 起動方法

Node.js 22以上とnpmを使用します。APIキーや環境変数は不要です。

```bash
npm ci
npm run dev
```

ブラウザで http://localhost:3000 を開いてください。

```bash
npm run build       # 本番ビルド（Webpack）
npm start           # 本番ビルドをローカルで起動
npm run typecheck   # TypeScriptチェック
npm test            # モックサービスの回帰テスト
```

開発サーバーと本番サーバーの既定ポートは同じです。同時に起動する場合は `npm start -- --port 3001` を使用してください。環境によってTurbopackのCSS処理用プロセスに制限があるため、本番ビルドはWebpackを明示しています。

## 3〜5分のデモ体験

1. 初期表示はデモAのホーム。重点テーマ・現在値・今日のアクションを確認。
2. 「あなたのアクションを見る」から、具体的な方法と「根拠を見る」を開く。
3. 「できた」「一部できた」を記録し、ホームの達成表示と「記録 → 行動の履歴」を確認。
4. 「記録」で体重・収縮期血圧・HbA1c・γ-GTPの推移を切り替える。
5. 「AI相談」で「ラーメンは食べない方がいい？」を選ぶ。現在のプロフィール・検査値が回答に反映される。
6. 右上の「デモモード」でB（血糖）、C（肝機能・飲酒）へ切り替える。Cでは医療機関への相談導線も体験できる。

新規入力はホームの「初めての方はこちら」または「マイページ → 別のプロフィールで入力を始める」。基本情報を入力し、健診結果は手入力または「サンプルデータを入力」で進めます。

## データモデル

`UserProfile`、`HealthCheck`、`HealthMetric`、`HealthAssessment`、`Recommendation`、`ActionPlan`、`Evidence`、`ActionLog`、`AIMessage` を定義しています。関連付けはIDで保持し、サンプル／手入力、モック生成、根拠の未検証状態を区別しています。

`Evidence` は `recommendation / evidence / source / evidence_level / population / expected_effect / notes` を保持します。ユーザーの保存単位は `UserData`、アプリ全体はバージョン付き `AppState` です。

## 判断・仮定

- 最初の3分で価値を理解できるよう、初期画面は操作可能なサンプルホームとし、初回説明・手入力への導線を上部に配置しました。
- 判定は数値を閾値で分類するものではなく、明示的なデモシナリオです。手入力は「評価未実施」、欠損は「未入力」と表示し、正常と扱いません。
- 手入力時の重点テーマ選択は、体験用のプランを選ぶ操作です。自動診断の結果ではありません。生活習慣は保存・閲覧できますが、推奨の細かな最適化は未実装です。
- 医学的な参考範囲を独自に作らず、「健診票の基準を確認」と表示します。数値の参考範囲・個人別目標・改善効果量は監修後に差し替える前提です。
- 受診判定 `getReferral()` はデモCでのみ明示的なフィクスチャを返します。手入力の数値から緊急性を判定しません。手入力のホームにも健診票で受診・再検査を勧められた方向けの相談入口を設けています。
- チャットの緊急・服薬キーワード分岐は、案内UXのサンプルです。症状を漏れなく拾うトリアージではありません。
- デモの検査履歴は当日から遡って作成します。グラフの変化は架空の値で、生活改善の実証や治療効果ではありません。
- 日付は端末のローカル日付です。同日の健診は追加順で最新を選び、過去日付の追加で最新結果が置き換わらないよう日付順で選択します。
- 「サンプルデータを入力」は既に入力した身長・体重を保持します。サンプルを編集すると手入力として扱います。
- 研究利用への同意は取得していません。実際の研究や医療目的のデータ利用は行いません。

## 本番化への接続ポイント

```text
Frontend
  → Application API
      → User Health Data
      → Evidence DB
      → AI / LLM
```

### User Health Data

`storage.ts` と `lifit-app.tsx` の `updateUser()`／保存処理を、認証済みAPIとRepositoryへ置換します。サーバーで入力検証・所有権確認・バージョン競合処理を行います。移行時に同意済みのデータだけを取り込み、ブラウザ内のサンプル履歴とは区別してください。

### 評価・受診判定

`services.ts` の `assessHealth()`／`getReferral()` を医師監修の評価サービスへ差し替えます。年齢・性別・妊娠・既往歴・治療中の薬・測定条件・施設基準・欠損を扱い、評価根拠とルールのバージョンを記録してください。BMI計算以外の医学的閾値は現状実装していません。

### Evidence DB

`services.ts` の `getEvidence(ids)` を `GET /api/evidence?ids=...` 等のApplication APIへ接続します。Recommendationの `evidenceIds` が参照点です。発行年、DOI、URL、本文抜粋、推奨強度、対象集団、禁忌、レビュー日、監修者、適用条件の型を拡張し、未検証・撤回・更新済みを区別します。ソース名だけで根拠を確定させない設計が必要です。

### AI API

`services.ts` の `askAI(question, profile, check)` がチャットの差し替え点、`createActionPlan(profile)` がプラン生成の差し替え点です。本番ではAPIキーをクライアントに置かずサーバーAPIで呼び出します。必要最小限の同意済みデータと取得したEvidenceを渡し、構造化出力を検証して `ActionPlan`／`AIMessage` に変換します。監修・禁忌チェック、根拠ID、失敗時の応答、タイムアウト、キャンセル、監査ログ、モデル評価を追加してください。

### 本番化で必要な作業

医療者によるコピー・評価・推奨のレビュー、個人情報と同意の設計、認証と認可、暗号化、監査、保存期間・削除、脅威分析、障害対応、運用監視、ユーザー検証、医療・研究利用の制度上の整理が必要です。実データを使う前に、プロトタイプのlocalStorage保存を本番データ基盤へ移してください。

## 検証

- 自動テスト：BMI、3シナリオ、Evidence参照、手入力・欠損を正常扱いしないこと、受診フィクスチャ、破損保存データ、AIのプロフィール参照・服薬／症状案内
- ブラウザ実操作：オンボーディング → 基本情報 → 未入力エラー → サンプル入力・編集 → 保存 → 再読み込み、行動記録 → ホーム・履歴、AI相談、デモA/B/Cの切替、相談 → 健診一覧、ブラウザの戻る操作
- 390pxのスマートフォン表示と1440pxのデスクトップ表示で確認。全5画面で390px幅の横はみ出しなし。入力途中で戻る操作をしても身長・体重を保持
- 開発中の依存更新で出た一時的なモジュール読込エラーは、更新完了・サーバー再起動後に解消
- 最終ブラウザ操作時のコンソールエラー・警告なし。依存関係の監査は0件、未使用変数チェックも通過
- WebMCPの状態読取と不正入力拒否をブラウザで確認済み。WebMCP対応ブラウザには読取専用の `lifit_read_demo_state` を公開。医療情報を操作するツールは公開していません

これは操作可能なモックの検証であり、医療安全性・臨床効果・アクセシビリティの正式認証ではありません。
